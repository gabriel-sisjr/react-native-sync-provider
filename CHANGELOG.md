# Changelog

All notable changes to **`@gabriel-sisjr/react-native-sync-provider`** are documented in this file.

The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

> **Pre-1.0 notice:** while the library is on `0.x`, minor version bumps (`0.x.0`) may include breaking changes. Every breaking change is summarized in [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md) and ships with a dedicated migration guide under `website/docs/migration/`.

### Added

- **Network quality.** `ConnectionState.networkQuality` grades the current link with the `NetworkQuality` levels `OFFLINE`, `POOR`, `MODERATE`, `GOOD` and `EXCELLENT`, on `getConnectionStatus()`, `useConnection()` and the `connection` of `useOfflineQueue()` and `useSyncSnapshot()`. It is `OFFLINE` exactly when the status is `DISCONNECTED` or `UNKNOWN`. Both platforms use one fixed table. With `healthCheckUrl` set, three back-to-back `HEAD` requests, each with a 2 s timeout, give a median latency: under 200 ms is `EXCELLENT`, 200–499 ms `GOOD`, 500–999 ms `MODERATE`, and 1000 ms or more, or two failed probes, `POOR`. With no measurement, an unmetered link is `GOOD` and a metered one `MODERATE`. Caps apply last: a metered or expensive link is at most `GOOD`, iOS Low Data Mode at most `MODERATE`, and an Android network without `NET_CAPABILITY_VALIDATED` at most `POOR`. Without `healthCheckUrl` nothing is measured, so the level never reaches `EXCELLENT`. A measurement starts 1000 ms after a network change and stays with that network, so the same network back within 30 s reuses it, and a gate check that finds it 30 s old or older starts one re-measurement in the background. Without `minNetworkQuality` nothing reads the gate, so only a network change or a new `healthCheckUrl` measures again. Probes go only to `healthCheckUrl`, never while offline, with no `defaultHeaders` and with `Cache-Control: no-cache`.
- **`SyncOptions.minNetworkQuality`.** An opt-in quality gate, unset by default. Below the minimum a flush runs no cycle: it emits `SYNC_FAILED` with the new `NETWORK_QUALITY_TOO_LOW` code, with no `SYNC_STARTED`, no history row and no item change, and resolves with the same 0/0 result as a paused flush. `POOR` blocks only `OFFLINE`, and `OFFLINE` gates nothing. The gate applies to `flush()`, `useAutoSync`, `drainUntilEmpty`, the Android retry kick and periodic worker, and the iOS BGTasks. The in-process retry timer holds a gated wake silently and runs it once the quality reaches the minimum, re-checking after 30, 60, 120, 240 and 480 seconds, then every 15 minutes. On iOS, a gated flush waits up to 1.5 s for the first path update before it grades the link.
- **Health check: `healthCheckUrl`, `healthCheckTtlMs` (default `60000`) and `healthCheckBackoffMs` (default `30000`).** Before a cycle claims its first item, the engine sends one `HEAD` to `healthCheckUrl`, unless a healthy result younger than the TTL exists. A `2xx` sample from a kept quality measurement counts as one, so the endpoint is not hit twice. A final `2xx` is healthy. Any other status, a transport error or a timeout skips the cycle the way the gate does, with the new `HEALTH_CHECK_FAILED` code, and starts a backoff during which cycles are skipped without a request. The next retry wake is the latest of the item's own deadline, the credential hold and the end of the backoff. Every automatic wake, the Android retry kick included, also waits at least 1000 ms after a failed check, so a backoff of `0` cannot make them spin; `flush()` keeps to the backoff alone. A healthy check ends the backoff, and so does every `configureSync` call.
- **Dead-letter queue: `listDeadLetter()`, `replayDeadLetter(id)`, `discardDeadLetter(id)` and the `ITEM_DEAD_LETTERED` event.** A permanently failed item now becomes a `SyncDeadLetterItem` (see Changed), with its request, `attempts`, `lastAttemptAt`, `lastErrorCode`, `deadLetteredAt` and an optional `lastErrorMessage`: the HTTP status line or the error message, at most 1024 characters and never headers or bodies. iOS writes the status line with the system's reason phrase (`HTTP 404 Not Found`), and Android with the server's, which is empty under HTTP/2 (`HTTP 404`). `ITEM_FAILED` keeps its real code, and `ITEM_DEAD_LETTERED` follows it synchronously with `errorCode: DEAD_LETTERED` and the real code in `metadata.lastErrorCode`. `listDeadLetter()` is ordered by `deadLetteredAt`, then `id`. `replayDeadLetter(id)` puts the item back under the same id and original `createdAt`, as `PENDING` with `attempts: 0` and `nextRetryAt: 0`, emits `ITEM_ENQUEUED`, does not flush, and respects `maxQueueSize`. `discardDeadLetter(id)` emits `ITEM_REMOVED`. An unknown id resolves with no change. The dead-letter queue is unbounded and never pruned.
- **Three error codes and one event type.** `NETWORK_QUALITY_TOO_LOW`, `HEALTH_CHECK_FAILED` and `DEAD_LETTERED` are appended to `SyncErrorCode`, for 15 codes, and `ITEM_DEAD_LETTERED` to `SyncEventType`, for 16 events.
- **Hooks.** `useSyncSnapshot().networkQuality` and `useSyncSnapshot().deadLetter`, always `undefined` in v0.2, are now populated. `networkQuality` is read with the connection, on mount and on every `CONNECTION_CHANGED`. `deadLetter` is read on mount and on `ITEM_DEAD_LETTERED`, `ITEM_REMOVED`, `ITEM_ENQUEUED` and `QUEUE_CLEARED`. Both stay `undefined` until their first read succeeds. `useConnection()` gains `networkQuality`, and `useSyncQueue`, `useOfflineQueue` and `useSyncSnapshot` also refresh their queue on `ITEM_DEAD_LETTERED`.
- **`configureSync` validates the new options in JS**, before any native call. `minNetworkQuality` must be a `NetworkQuality` value, `healthCheckUrl` an absolute `http(s)` URL, and both durations finite numbers of at least `0`. The first invalid field, in that order, sets the code: `INVALID_URL` for `healthCheckUrl`, `INVALID_PAYLOAD` for the others. `validationErrors` lists every issue, and `ValidationIssue.value` is never set for `healthCheckUrl`. The four options are persisted for cold-start workers, `getSyncConfig()` returns them only when they were set, and a stored value that cannot be used loads as unset.

### Changed

- **Permanently failed items move to a dead-letter store**, on both platforms, instead of staying in the queue as `FAILED` rows. That covers attempts exhausted, responses that are not retried, and a 401 or 403 under a configuration set in the current process. The move is one transaction. Rows that were already `FAILED` move on upgrade, through Room v2→v3 on Android, v1→v2→v3 included, and Core Data model v3 on iOS, with explicit mappings from v1 and v2. Pending rows are untouched. A migrated row has no `lastErrorMessage` and takes its last attempt time, or else its enqueue time, as `deadLetteredAt`, and one with no usable code reports `MAX_ATTEMPTS_EXCEEDED`. On iOS the migration runs before the store loads, BGTask launches included. If it fails, the original store is untouched, that launch runs without a store, so every call rejects with `NATIVE_MODULE_UNAVAILABLE`, and the next launch retries. Both migrations are roll-forward only: downgrading an Android install wipes the store, and a downgraded iOS build cannot open it. See [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md).
- **android:** dead letters count toward no capacity cap. Failed rows used to count toward `maxQueueSize`, so `QUEUE_FULL` now arrives later: the cap counts pending and in-flight items only.
- **`clearQueue()` also deletes dead letters**, still with one `QUEUE_CLEARED`. **`removeItem(id)`** falls through to the dead letter with that id when no queued item has it, and returns `true` when either store deleted a row.
- **`CONNECTION_CHANGED` fires only when a reported field changes**: `status`, `type`, `isInternetReachable`, `isExpensive` or `networkQuality`. It never fires for a duplicate, and Android never for the state it starts in; iOS starts at `UNKNOWN`, so its first path report emits one. iOS used to emit it on every path update, and Android already behaved this way. It is also emitted when only `networkQuality` changed, with an unchanged `connectionStatus`. iOS delivers it synchronously, Android asynchronously.
- **android:** connectivity follows only the default network. Losing a secondary network, such as cellular alongside Wi-Fi or a VPN that does not apply to the app, no longer reports `DISCONNECTED`, and a VPN that was the default network hands over without a false disconnect.
- **android:** on Android 11 (API 30) and later, a temporarily unmetered link, as some 5G plans provide, reads as `CONNECTED` with `isExpensive: false` instead of `METERED`, and as `METERED` again when the exemption is withdrawn.
- **`ConnectionState.networkQuality` and `UseConnectionResult.networkQuality` are required.** Code that only reads them is unaffected. Hand-built values, such as test fixtures and mocks of `getConnectionStatus`, stop compiling until they set the field. See [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md).
- **`react-native-nitro-modules` 0.35.8 or later is required.** The peer range moves from `^0.35.6` to `^0.35.8`: 0.35.8 or later, and still below 0.36. In 0.35.6 and 0.35.7 the Swift `Promise` had no lock, so a promise could settle before the generated bridge attached its listeners, and the JS promise never settled. The fix, [Nitro PR #1338](https://github.com/margelo/nitro/pull/1338) ("Fix `Promise<void> was destroyed!` race condition by synchronizing Swift `Promise` operations"), was first published in 0.35.8 on npm. Nitro's GitHub has no v0.35.8 release: the fix is listed in the [v0.35.9 release notes](https://github.com/margelo/nitro/releases/tag/v0.35.9), which compare v0.35.7 with v0.35.9. To upgrade, run `yarn add "react-native-nitro-modules@^0.35.8"`, then `cd ios && bundle exec pod install`. See [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md).

### Fixed

- **ios:** `getSyncConfig`, `getConnectionStatus`, `isBackgroundSyncEnabled`, `addListener` and `removeListener` now return already-settled promises. With `react-native-nitro-modules` 0.35.6 and 0.35.7, a promise that settled before the bridge attached its handler could leave the JS promise pending forever. The upstream fix, a lock in Nitro's Swift `Promise`, arrives with 0.35.8, which this release requires (see Changed). The settled promises stay, so these calls do not depend on it.
- **ios:** an item whose attempts already reached `maxAttempts`, as after `configureSync` lowered it, was sent once more. It is now dead-lettered without a request, as on Android: `ITEM_FAILED` with `MAX_ATTEMPTS_EXCEEDED`, its stored attempt count and no `statusCode`, then `ITEM_DEAD_LETTERED`, with `lastErrorMessage` set to `Retry budget exhausted`. A `maxAttempts` below `1` reads as `1`, so a new item is still sent once.
- **hooks:** `useAutoSync` flushed on the first `CONNECTION_CHANGED` after mount whenever it reported `CONNECTED`, even when the status had not changed, for example when only the network quality changed. It now reads the starting status when it is enabled and flushes only when the status changes to `CONNECTED`, or to `METERED` with `flushOnMetered`. If that read fails, the first event only sets the status the next ones are compared with.
- **ios:** an item removed or cleared after a cycle read the queue, but before its own request started, was still sent once, headers and body included, and got outcome events of its own. It is now skipped: no request, no `ITEM_SUCCEEDED`, `ITEM_RETRYING` or `ITEM_FAILED`, and it does not count as attempted.
- **android:** with `defaultHeaders` restored from storage, a cycle sends its first item alone and the rest after its answer. An item removed or cleared during that first request, as by a logout's `clearQueue()`, was still sent once with the restored headers and got outcome events of its own. It is now skipped the same way.
- **android:** `CONNECTION_CHANGED` could fire once for the starting state, when the system reported the network while the monitor was registering its callback. The monitor now reads the state before it registers and never emits for the starting state.

### Fixed

- **android:** after a 401 or 403 on a request sent with `defaultHeaders` restored from storage, every retry wake in the same process now waits for the credential hold to end, as the end of a cycle already did and as on iOS. That covers `resumeSync()`, a JS attach or reload and the recovery re-arm, for both the in-process retry timer and the `WorkManager` retry kick. Every `configureSync` call clears the hold. The hold lives in memory on both platforms, so a process restart drops it: the rejected item keeps its own `nextRetryAt`, but another due item can wake the queue and send one request with the rejected credential, which sets a new hold. The periodic worker and the iOS BGTasks are not retry wakes and do not wait for the hold, so a window that opens during one can also cost a request.

### Documentation

- Corrected the retry bookkeeping on `SyncItem`. `nextRetryAt: 0` means the item is eligible now, not that it was never attempted, and a positive value means a retry cooldown or a credential hold is pending. `attempts` counts the attempts recorded for the item, so `0` does not mean it was never tried: Android records an attempt with its outcome, and a credential hold does not spend one.
- Documented what `flush()` returns while the engine is paused or stored `defaultHeaders` cannot be read: no cycle runs, no event is emitted, no history row is written, and the counts are 0/0. Android returns `0` for `startedAt` and `finishedAt`, and iOS the time of the call.
- Corrected `isPaused` and `lastResult` in the hooks. `isPaused` follows `PAUSED` and `RESUMED` only, so a hook mounted during a pause from earlier in the same JS session reads `false`. After a launch or a JS reload `false` is correct, because the launch clears the pause. `useSyncSnapshot().lastResult` comes from the persisted history, so it can predate the current session.
- Corrected the `BACKGROUND_SYNC_STARTED` and `BACKGROUND_SYNC_COMPLETED` payloads. Neither platform sets `errorCode`: a failed window reports its code on the cycle's `SYNC_FAILED`. iOS sets `metadata.kind`, plus `metadata.ok: "false"` when the flush failed. Android emits the pair from the periodic worker only, and no `BACKGROUND_SYNC_COMPLETED` when the worker's flush throws.
- Documented that `getSyncConfig()` returns no `defaultHeaders` while the stored copy cannot be read, so passing its result back to `configureSync` or `setConfig` deletes the stored headers. The examples now take `defaultHeaders` from the app's session.
- Documented that `useAutoSync` keeps flushing under `strategy: MANUAL`, because it never reads the strategy. Pass `enabled: false` for a manual flow.
- Documented that `removeItem` removes an item in any status, including one that failed permanently, and does not cancel a request already in flight.
- Removed the sketched signature of the JS-side retry override. It is planned for a later release, with no committed shape.
- Corrected earlier entries in this file: `foregroundOnly` still lets Android schedule its recovery job, the Android jitter range is `[0.75, 1.25)`, no stable 0.1.0 or 0.1.1 was published, and the `yarn test:ios` script never existed.
- Aligned the documentation with the conventions of react-native-background-location. The README is now a landing page, and the sections it dropped live on the site. Callouts are blockquotes, and mermaid diagrams render and are validated during the docs build. New pages: a migration guide per version (v0.2.0 and v0.3.0), Platform Comparison, Crash Recovery, Battery Optimization, CI/CD Pipeline and Publishing. Troubleshooting gains an FAQ. Statements that contradicted the code were corrected.

## [0.2.0] - 2026-11-03

### Added

- **`useSyncSnapshot` hook.** Read-only aggregator of connection, queue and sync-engine state, driven by one `addSyncEventListener` subscription. Unlike [`useOfflineQueue`](https://gabriel-sisjr.github.io/react-native-sync-provider/docs/api-reference/hooks/useOfflineQueue) it exposes no actions. `UseSyncSnapshotResult` carries `connection`, `size`, `items`, `isSyncing`, `isPaused`, `progress`, `lastResult`, `isWaitingForConnection` and `error`. It is safe to call before the native module loads and inert on web.
- **Forward types for v0.3.** `NetworkQuality` and `SyncDeadLetterItem` are exported so consumer types can depend on their final shape. They appear only as the optional `UseSyncSnapshotResult.networkQuality` and `UseSyncSnapshotResult.deadLetter` fields, which are always `undefined` in v0.2.
- **Structured `validationErrors` on `SyncError`.** `SyncError` gains an optional `validationErrors?: ValidationIssue[]`, and the `ValidationIssue` type (`{ field, reason, value?, itemIndex? }`) is exported. Validation failures from `enqueue` and `enqueueBatch` now list every violation, not just the first. `value` is set only for `method`, `priority` and `contentType`, because errors end up in logs and the other fields can hold credentials and personal data. `reason` never contains the URL. Single-item `enqueue` keeps its historical `message`, which can contain the URL.
- **`drainUntilEmpty()` and `cancelDrain()`.** A JS-side loop over the existing bridge, bounded by `DrainOptions` (`maxIterations` default `32`, `timeoutMs` default `60000`, optional `delayBetweenCyclesMs`). It resolves a `DrainResult` (`iterations`, `itemsDispatched`, `queueRemaining`, `stoppedReason`). `EMPTY` means `getQueueSize() === 0 && isSyncing() === false`. `timeoutMs` and `cancelDrain()` are hard stops: every wait races them, and a native cycle already running keeps going after the drain returns. The loop sleeps until the soonest cooldown by itself and stops at once with `TIMEOUT` if that moment is past the deadline. It does not flush while `getConnectionStatus()` is `DISCONNECTED`, so it waits for the network and ends in `TIMEOUT` with items intact. `maxIterations` counts real flushes, and non-finite options fall back to their defaults. Only one drain may run per process: a concurrent call throws the new `DRAIN_ALREADY_ACTIVE` code, the 12th `SyncErrorCode`. Adds the `DrainOptions`, `DrainResult` and `DrainStoppedReason` types.
- **`BackgroundSyncOptions.foregroundOnly`.** Kill switch for background work, default `false`. When `true`, the library schedules no background dispatch (no `BGTaskScheduler` requests, no `WorkManager` periodic or one-time flush jobs), cancels what it had scheduled, and iOS stops using the background `URLSession`. Sync then progresses only while the app is alive: through `flush()`, `drainUntilEmpty()`, `useAutoSync`, and the in-process retry timer, which this flag does not stop. Launch and boot recovery still run, so Android still schedules its one-time recovery job, which makes no network call. `isBackgroundSyncEnabled()` reports intent, so it stays `true`.
- **`SyncItem.attempts` and `SyncItem.nextRetryAt`.** Per-item retry bookkeeping, returned by `getPendingItems()`. `attempts` counts the dispatch attempts recorded for the item across cycles, so `0` means none was recorded, not that the item was never tried. `nextRetryAt` is `0` when the item is eligible now, and a positive epoch-ms deadline while a retry cooldown or a credential hold is pending. An item is eligible when `nextRetryAt <= now`. Both are real values, returned verbatim and never translated to `undefined`.
- **`useSyncContext()` hook and `SyncProviderContextValue.hasProvider`.** `useSyncContext()` reads the `<SyncProvider>` context. `hasProvider` tells "no Provider mounted" (`false`) apart from "Provider mounted, config still loading" (`true`). Like every hook, it never throws outside a Provider.
- **In-process retry timer, on both platforms.** A single-shot timer armed for the soonest cooldown at the end of every cycle, on engine start after recovery, on `configureSync` and on `resumeSync`, so a failed item comes back on its own while the app runs. If it fires offline it does not flush: it remembers the wake and flushes when connectivity returns, so an offline device spends no attempts. `pauseSync` and `strategy: MANUAL` suppress it. It does not exist in a process with no JS-facing hybrid, such as a worker, a boot broadcast or an iOS background launch where JS never reaches the library.
- **Retry kick on Android.** A delayed one-time `WorkManager` job armed alongside the timer, so a cooling item is retried even if the process dies. It runs only with `enableBackgroundSync` active, `foregroundOnly` off, `strategy` other than `MANUAL` and the engine not paused. It honors the same constraints as the periodic work, and `disableBackgroundSync()` cancels it. iOS has no kick: its background path is `BGTaskScheduler`.
- **Cold-start configuration.** `configureSync` now persists the options, so a worker or BGTask in a fresh process honors `maxAttempts`, `batchSize`, `requestTimeoutMs` and the rest. `defaultHeaders` are encrypted at rest with no new dependency: Android Keystore AES-256-GCM, iOS Keychain (`AfterFirstUnlockThisDeviceOnly`, not synchronized). `configureSync` without `defaultHeaders` deletes the stored copy, which makes it the logout path. If stored headers cannot be read, nothing is dispatched and items wait. If a process that has not called `configureSync` gets a 401 or 403, the item stays `PENDING`, no attempt is spent, the next try waits at least 60 seconds and the cycle stops, so an expired token costs one request per wake. The library does not refresh tokens: apps must call `configureSync` when the token changes, and a process with no JS cannot renew one.
- **iOS background path.** BGTask handlers now register at process start through `+load`, so they work on a launch with no JS loaded and need no `AppDelegate` call. An identifier missing from `BGTaskSchedulerPermittedIdentifiers` no longer crashes: that handler is skipped, and `enableBackgroundSync` rejects when `com.gabriel-sisjr.syncprovider.background` is the one missing. `BackgroundSyncOptions`, including `foregroundOnly`, persist across relaunches, and the handlers continue the task chain on their own. The Privacy Manifest now declares `NSPrivacyAccessedAPICategoryUserDefaults` / `CA92.1`.

### Changed

- **`enqueueBatch` throws a single umbrella error on invalid input.** When any item fails validation, `enqueueBatch` throws one `SyncError(INVALID_PAYLOAD)` whose `validationErrors` carries every issue across every item, each tagged with its `itemIndex`, instead of the first bad item's specific code. Array holes are rejected too. No items are enqueued when any issue is present. Code that matched `SyncErrorCode.INVALID_URL` from a batch call now sees `INVALID_PAYLOAD`. Single-item `enqueue` still throws the first violation's specific code. See [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md).
- **`getQueueSize()` and `getPendingItems()` cover `PENDING` items only, on both platforms.** Cooling items are included. `IN_FLIGHT` and `FAILED` items are not: Android stopped counting `FAILED` and `IN_FLIGHT` rows, and iOS stopped returning them. `getPendingItems()` returns dispatch order on both. Capacity checks are unchanged, so Android's cap still counts `FAILED` rows until the v0.3 dead-letter queue. See [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md).
- **`MANUAL` scope.** `MANUAL` suppresses the in-process retry timer and the Android retry kick. It does not make periodic workers or BGTasks inert: calling `enableBackgroundSync` is an explicit request, and `foregroundOnly` is the kill switch for background work.
- **Pause is persisted.** Workers and BGTasks stay inert while the app is dead, and Android now checks the pause inside the dispatcher, so workers obey it. A pause lasts until `resumeSync()` or the next launch that reaches the library, including a JS reload. A launch clears it without emitting `RESUMED`.
- **Persisted retry cooldown on Android.** A retriable failure writes `nextRetryAt`, measured from the end of the attempt, and `claimPending` skips the item until that deadline passes, served by a new `(status, nextRetryAt)` index. The in-cycle `delay()` retry loop is gone: each cycle makes at most one attempt per item, and `attempts` counts across cycles. `SyncWorker` returns `Result.success()` on any completed flush, so WorkManager's own backoff is reserved for whole-worker failures. Retriable items now wait between attempts even after process death or reboot.
- **Empty cycles on Android.** A cycle with nothing eligible now emits `SYNC_SUCCEEDED` and records a 0/0 result, as iOS already did. Every path that starts a cycle ends it with a terminal event.
- **Schema migrations: Room v1→v2 on Android, Core Data model v2 on iOS.** Both add the persisted `nextRetryAt`, and Android also adds the `(status, nextRetryAt)` index. The v1 Core Data model stays in the bundle. Both are roll-forward only: a forward upgrade migrates data, but downgrading an Android install past v0.2 wipes the queue (`fallbackToDestructiveMigrationOnDowngrade`). See [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md).
- **iOS minimum deployment target raised `13.0` → `15.0`.** `SyncProvider.podspec` now declares iOS `15.0`. The implementation already relied on `URLSession.data(for:)` (iOS 15+), and the `13.0` floor only compiled because the example app overrode `IPHONEOS_DEPLOYMENT_TARGET`. React Native 0.85 raises the built pod to `15.1`. The always-true `#available(iOS 13.0, *)` guards were removed. This is a platform-requirement change, not a JS/TS API break. See [`BREAKING_CHANGES.md`](./BREAKING_CHANGES.md).

### Fixed

- **ios:** retry cooldown is now applied between attempts. `RetryPolicyEvaluator.nextDelayMs` had no production call site and failed items went straight back to `PENDING`, producing a hot retry loop against a degraded server. The dispatcher now persists the backoff as `nextRetryAt`, measured from the end of the attempt, and the fetch predicate skips cooling items. `countPending` still counts them, and launch recovery preserves cooldowns.
- **ios:** a non-retryable failure keeps its real code, including on the last attempt, so a 401 stays `UNAUTHORIZED`. `MAX_ATTEMPTS_EXCEEDED` now applies only to a retriable failure with no attempts left, as on Android.
- **android:** retry jitter corrected to `[0.75, 1.25)` equal jitter. `RetryPolicyEvaluator` applied full jitter over `[0, capped]` and capped before jittering, so delays collapsed toward `0`. It now jitters the raw delay and applies the cap afterwards, matching JS and iOS.
- **android:** a worker in a fresh process now resets rows a dead process left `IN_FLIGHT` before it flushes, as iOS BGTasks already did, so those items no longer wait for the next launch, boot or app update. A persisted pause or `foregroundOnly` blocks the worker, recovery included. Recovery keeps `nextRetryAt`, so a row still cooling is reset but not sent.
- **ios, android:** the Fibonacci backoff no longer overflows at attempt 93.
- **`useAutoSync`:** the interval and the `flushOnAppForeground` trigger no longer flush while the connection status is `DISCONNECTED`, or when the status cannot be read, so offline ticks spend no retry attempts. `UNKNOWN` and `METERED` still flush, and the reconnect trigger is unchanged. Remove any `enabled: isOnline` workaround: while `enabled` is `false` the hook is not subscribed, so the reconnect trigger cannot fire.
- **`SyncProvider` context:** `<SyncProvider>` reads the native config even when `configureSync` rejects, so consumers see the config the engine kept instead of waiting forever. `useSyncConfig` treats a context value carrying `config` as provider-present, and its `setConfig` updates only the calling hook.
- **Entry parity:** `SyncProviderProps` is now exported from the native entry, and the web `useAutoSync` takes `UseAutoSyncExtraOptions`.
- **Package contents:** the npm package now ships `ios/Database/SyncProvider.xcdatamodeld/.xccurrentversion`, and no longer ships native tests or `lib/typescript/website`.

### Documentation

- Removed every claim that `AUTOMATIC` flushes natively on enqueue or when connectivity returns. Neither exists: `useAutoSync` is the mechanism. `OPPORTUNISTIC` is documented as reserved, since it currently behaves like `AUTOMATIC`.
- Corrected the iOS setup: removed the `AppDelegate` registration sample and its `SyncProviderBackgroundTaskRunner` class, which never existed, and documented the `handleEventsForBackgroundURLSession` forwarding, both BGTask identifiers and `UIBackgroundModes`.
- Documented options that are accepted but have no effect (`persistQueue`, `taskIdentifier`, `UseAutoSyncOptions.backgroundSync`, `UseAutoSyncOptions.flushOnForeground`), and that `DUPLICATE_ITEM` is reserved and `QUEUE_FULL` reaches JS as `INVALID_PAYLOAD`.
- Rewrote the idempotency guide around a key generated before `enqueue` and sent in `headers`, because the native ULID is not sent with the request.

### Internal

- **iOS:** demoted the Core Data entity classes `SyncItemEntity` and `SyncResultEntity` and their members from `public` to internal. The `public` access level leaked them into the generated `SyncProvider-Swift.h` bridging header and broke Objective-C translation units in the iOS CI build. No public API impact. The example `AppDelegate` now calls the renamed `HybridSyncProvider.handleBackgroundURLSessionEvents`.
- **test:** added an entry-parity guard. `src/__tests__/webParity.test.ts` uses the TypeScript compiler to assert that `src/index.tsx` and `src/index.web.tsx` export the same names, each with the same kind and shape, and `src/__tests__/webEntry.test.tsx` asserts that the web entry stays inert.
