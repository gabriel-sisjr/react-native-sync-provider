# Migration Guide: v0.2.x to v0.3.0

> **Roll-forward only.** No function, hook or error code was removed, and the quality gate and the health check are opt-in. Four things change for every app: `react-native-nitro-modules` must be 0.35.8 or later, permanently failed items move to a dead-letter queue, `networkQuality` is a required field, and connection events fire only on real changes. The stores migrate automatically on first launch, and there is no supported downgrade. Read the whole list before you ship.

## What Changed

- **`react-native-nitro-modules` floor.** The peer range moves from `^0.35.6` to `^0.35.8`: 0.35.8 or later, and still below 0.36. Apps on 0.35.6 or 0.35.7 must upgrade, and package managers that check peer ranges warn about or reject those versions. Apps already on 0.35.8 or a later 0.35.x release have nothing to do.
- **Dead-letter queue.** An item that fails permanently moves, in one transaction, from the queue to a separate dead-letter store. That covers attempts exhausted, responses that are not retried, and a 401 or 403 under a configuration set in the current process. `ITEM_FAILED` is followed by `ITEM_DEAD_LETTERED`, except for an item removed or cleared while its request was in flight. [`listDeadLetter`](../api-reference/functions.md#listdeadletter), [`replayDeadLetter`](../api-reference/functions.md#replaydeadletter) and [`discardDeadLetter`](../api-reference/functions.md#discarddeadletter) are new. Dead letters count toward no capacity cap, and nothing prunes them.
- **`removeItem` and `clearQueue`.** `removeItem(id)` falls through to the dead letter with that id, and `clearQueue()` deletes every dead letter too, with one `QUEUE_CLEARED`. Code that removed failed items by id keeps working.
- **Queue cap on Android.** Android counted `FAILED` rows toward `maxQueueSize`. Its cap now counts pending and in-flight items, so a queue that used to be full of failed rows accepts items again. The iOS cap counts `PENDING` items, as before.
- **Required `networkQuality`.** `ConnectionState.networkQuality` and `UseConnectionResult.networkQuality` are required, which puts the field on the `connection` of `useOfflineQueue` and `useSyncSnapshot` too. `SyncEventType` gains `ITEM_DEAD_LETTERED`, and `SyncErrorCode` gains `NETWORK_QUALITY_TOO_LOW`, `HEALTH_CHECK_FAILED` and `DEAD_LETTERED`.
- **`CONNECTION_CHANGED` on real changes only.** Both platforms emit it only when `status`, `type`, `isInternetReachable`, `isExpensive` or `networkQuality` changes, never for a duplicate. Android already behaved this way.
- **Android connectivity.** Android follows only the default network, the one the app's traffic uses. On Android 11 (API 30) and later, a temporarily unmetered link, as some 5G plans provide, reads as `CONNECTED` with `isExpensive: false`, and as `METERED` again when the OS withdraws the exemption. `NetworkQuality` follows the same link: an unmetered link with no measurement is `GOOD`.
- **Quality gate and health check.** `SyncOptions` gains `minNetworkQuality`, `healthCheckUrl`, `healthCheckTtlMs` and `healthCheckBackoffMs`. All four start unset.
- **Persisted data.** Android moves from Room v2 to v3, which adds the dead-letter table. iOS adds Core Data model v3, with explicit mappings from v1 and v2. Both move the existing `FAILED` rows to the dead letters.

## Migration Steps

> **Important — Roll-forward only:** The upgrade migrates the stores automatically, and there is no supported downgrade. Downgrading an Android install wipes the queue and the dead letters. See [Rolling back](#rolling-back-from-v03).

### Step 1: Upgrade and Rebuild

1. Upgrade the package, and `react-native-nitro-modules` to 0.35.8 or later, below 0.36: `yarn add "react-native-nitro-modules@^0.35.8"`, or `npm install "react-native-nitro-modules@^0.35.8"`. In 0.35.6 and 0.35.7, an iOS call could leave its JS promise pending forever. The fix was first published in 0.35.8 on npm. Nitro's GitHub has no v0.35.8 release and lists the fix in its v0.35.9 notes.
2. On iOS, run `cd ios && bundle exec pod install`, then rebuild. The pod ships a new Core Data model version.
3. On Android, rebuild. No new permission is needed.

### Step 2: What Migrates Automatically

- **Failed items.** Items that had failed permanently, which v0.2 kept as unlisted `FAILED` rows, move to the dead-letter queue when the upgraded library first opens its store: Room v2→v3 on Android, v1→v2→v3 included, and Core Data model v3 on iOS, with explicit mappings from v1 and v2. Read them with [`listDeadLetter`](../api-reference/functions.md#listdeadletter). A migrated item has no `lastErrorMessage` and takes its last attempt time, or else its enqueue time, as `deadLetteredAt`, and one with no usable error code reports `MAX_ATTEMPTS_EXCEEDED`.
- **Pending items.** Untouched, with their attempts and cooldowns.
- **Configuration.** The persisted options carry over. `minNetworkQuality` and the health-check options start unset, so flushes behave as in v0.2 until you opt in.

> **Note — iOS migration:** The iOS migration runs before the store loads, on every launch path, BGTask launches included. If it fails, the original store is untouched and the next launch tries again. Until then, every call that reads or writes the queue, the dead letters or the history rejects, with the facade's fallback code (`INVALID_PAYLOAD`, or `NETWORK_ERROR` for `flush`) and the store error in `message`, while `configureSync`, `getSyncConfig` and `getConnectionStatus` still work. See [Native Rejections](../api-reference/errors.md#native-rejections). Stores written from 0.1.1-rc on migrate. A store written by the 0.1.0-beta prerelease is not a recognized source: it fails to load the same way, and the file is kept.

### Step 3: Compile-Time Fixes

`ConnectionState.networkQuality` and `UseConnectionResult.networkQuality` are required. Code that only reads these types compiles as before. Hand-built values, usually test fixtures and mocks of `getConnectionStatus` or `useConnection`, need the field:

```ts
const online: ConnectionState = {
  status: 'CONNECTED',
  type: 'WIFI',
  networkQuality: 'GOOD',
};

const offline: UseConnectionResult = {
  status: 'DISCONNECTED',
  type: 'NONE',
  isOnline: false,
  isMetered: false,
  networkQuality: 'OFFLINE',
};
```

Keep the invariant the library keeps: `OFFLINE` exactly when `status` is `DISCONNECTED` or `UNKNOWN`. With no `healthCheckUrl`, an online link usually reports `GOOD` when unmetered and `MODERATE` when metered; an Android network that is not validated reports `POOR`, and iOS Low Data Mode at most `MODERATE`.

`SyncEventType` gains `ITEM_DEAD_LETTERED`, and `SyncErrorCode` gains `NETWORK_QUALITY_TOO_LOW`, `HEALTH_CHECK_FAILED` and `DEAD_LETTERED`. Add them to any exhaustive `switch` that ends in a `never` check. If you mock the library in tests with an explicit factory, add `listDeadLetter`, `replayDeadLetter` and `discardDeadLetter` to it.

### Step 4: Handle Dead Letters

An item that fails permanently now moves, in one transaction, to the dead-letter queue: `ITEM_FAILED` reports the real code, and `ITEM_DEAD_LETTERED` follows. Nothing retries a dead letter, nothing prunes the dead-letter queue, and it counts toward no capacity cap.

```ts
import {
  discardDeadLetter,
  flush,
  listDeadLetter,
  replayDeadLetter,
  SyncErrorCode,
} from '@gabriel-sisjr/react-native-sync-provider';

// For example after a token refresh.
for (const item of await listDeadLetter()) {
  if (item.lastErrorCode === SyncErrorCode.UNAUTHORIZED) {
    await replayDeadLetter(item.id); // back to the queue, attempts 0
  } else {
    await discardDeadLetter(item.id);
  }
}
await flush(); // a replay does not flush by itself
```

- **Where to read them.** [`listDeadLetter`](../api-reference/functions.md#listdeadletter), oldest first, or [`useSyncSnapshot().deadLetter`](../api-reference/hooks/useSyncSnapshot.md) in a component.
- **Replay.** [`replayDeadLetter`](../api-reference/functions.md#replaydeadletter) puts the item back under the same id, with `attempts: 0` and `nextRetryAt: 0`. It respects `maxQueueSize`: on a full queue it rejects with `INVALID_PAYLOAD` and keeps the dead letter.
- **Discard.** [`discardDeadLetter`](../api-reference/functions.md#discarddeadletter), or `removeItem(id)`, which falls through to the dead letter with that id.
- **Logout.** `clearQueue()` deletes the dead letters too. They keep their request headers and body, so keep it in the logout path. It does not need to wait for a running cycle: an item whose request has not started is not sent, and a request already in flight is not cancelled, but its item is never written back. See [What a Purge Stops](../api-reference/functions.md#what-a-purge-stops).
- **Android cap.** Failed items no longer count toward `maxQueueSize`. Code that removed them on `ITEM_FAILED` only to stay under the cap can go, but the dead-letter queue is unbounded, so discard what you will not replay.

See [Dead-letter flows](../guides/error-handling.md#dead-letter-flows) for more patterns.

### Step 5: Review Behavior Your Code May Rely On

| Area | What changed | What to do |
| --- | --- | --- |
| Permanent failures | Moved to the dead-letter queue. `ITEM_FAILED` is followed by `ITEM_DEAD_LETTERED`. | Handle dead letters as in Step 4. |
| `removeItem`, `clearQueue` | Also delete dead letters. `removeItem` returns `true` when either store deleted a row. | Nothing, unless you counted on dead letters surviving a `clearQueue()`. |
| Android `maxQueueSize` | Counts pending and in-flight items. Failed items no longer count. | Drop purges that only kept the queue under the cap. |
| `CONNECTION_CHANGED` | Fires only when a reported field changes, never for a duplicate, and on Android never for its starting state. iOS starts at `UNKNOWN`, so its first path report emits one. iOS used to emit it on every path update. Also fires when only `networkQuality` changed, with the same `connectionStatus`. Both platforms deliver it to JS asynchronously, after the new state is stored. | Read the initial state with `getConnectionStatus()`. Compare `connectionStatus` with the previous value before acting on a transition, as `useAutoSync` does. |
| Android connectivity | Follows the default network only: losing a secondary network no longer reports `DISCONNECTED`. | Expect fewer false disconnects. |
| Android 11 (API 30) and later | A temporarily unmetered link reads as `CONNECTED` with `isExpensive: false`, not `METERED`. | Check `type === 'CELLULAR'` too if you must tell cellular apart. |
| iOS synchronous calls | `getSyncConfig`, `getConnectionStatus`, `isBackgroundSyncEnabled`, `addListener` and `removeListener` return settled promises, which fixes a promise that could stay pending forever with `react-native-nitro-modules` 0.35.6 and 0.35.7. The required 0.35.8 fixes it upstream too. | Nothing. |

### Step 6: Adopt the Quality Gate and the Health Check (Optional)

Both are off until you set them, through `configureSync` or `<SyncProvider options>`:

```ts
import {
  configureSync,
  NetworkQuality,
} from '@gabriel-sisjr/react-native-sync-provider';

await configureSync({
  ...SYNC_OPTIONS, // your existing options
  defaultHeaders: session.headers, // keep them on every call
  minNetworkQuality: NetworkQuality.POOR, // skip cycles while offline
  healthCheckUrl: 'https://api.example.com/health',
  healthCheckTtlMs: 60_000, // the default
  healthCheckBackoffMs: 30_000, // the default
});
```

Before you turn them on:

- **Pick the minimum.** `POOR` is the most permissive gate: it only stops flushes while the quality is `OFFLINE`, which also protects a manual `flush()` from spending attempts offline. Without `healthCheckUrl`, `GOOD` excludes metered links, Android links without `NET_CAPABILITY_VALIDATED` and iOS links in Low Data Mode, and `EXCELLENT` never passes. See [The quality gate](../guides/connectivity-detection.md#the-quality-gate).
- **Pick the endpoint.** The `HEAD` carries no `defaultHeaders`, so `healthCheckUrl` must answer it with a `2xx` without authentication. It is also the only target of the latency measurement. Expect three `HEAD`s per measurement. One is taken when the device moves to a network or the URL changes, when a path or capability update finds the last one 30 s old or older (on Android, a `configureSync` call too), and, with `minNetworkQuality` set, when the gate finds it 30 s old or older. Android also takes one when its monitor starts, at the first library call in a process with JS, and at once when the network's validation changes. The health check adds one `HEAD` per cycle, except while a healthy result younger than `healthCheckTtlMs` exists, which a `2xx` sample from a kept measurement can provide, and while a backoff runs. After a failure, the next check goes out when the backoff ends. Automatic retry wakes also wait at least 1000 ms, so a backoff of `0` cannot make them spin, while a `flush()` call checks again at once. See [Health check](../guides/connectivity-detection.md#health-check).
- **Skipped cycles are not failures.** A skipped flush emits `SYNC_FAILED` with `NETWORK_QUALITY_TOO_LOW` or `HEALTH_CHECK_FAILED`, with no `SYNC_STARTED` and no item change. If your UI reacts to `SYNC_FAILED`, check `errorCode`. `drainUntilEmpty()` counts a skipped flush as an iteration, so on a gated link it ends with `MAX_ITERATIONS` or `TIMEOUT`.
- **Background windows.** A worker or BGTask the gate or the health check skips completes normally, and the window is spent. See [Background Sync](../guides/background-sync.md#when-the-gate-or-the-health-check-skips-a-window).
- **Validation.** `configureSync` now rejects an invalid value for these four fields before any native call. The first invalid field, in the order `minNetworkQuality`, `healthCheckUrl`, `healthCheckTtlMs`, `healthCheckBackoffMs`, sets the code: `INVALID_URL` for `healthCheckUrl`, `INVALID_PAYLOAD` for the others. A `healthCheckUrl` of the right shape with no usable host, such as `https://:8080`, passes this check and is rejected natively instead, reaching JS as `INVALID_PAYLOAD`.

### Rolling Back {#rolling-back-from-v03}

> **Important — Android downgrade wipes the store:** Downgrading an Android install to a v0.2 build triggers `fallbackToDestructiveMigrationOnDowngrade()` and wipes the persisted queue and the dead letters. There is no supported downgrade.

A v0.2 iOS build cannot open the migrated store: the load fails as incompatible, and the calls that use the store reject with the facade's fallback code (`INVALID_PAYLOAD`, or `NETWORK_ERROR` for `flush`) until the app runs v0.3 again. The store file is kept, not deleted. That iOS outcome follows from the code and has not been exercised in a test.

If you must roll back, first drain the queue with `drainUntilEmpty()` and confirm `stoppedReason === 'EMPTY'`. Then read the dead letters with `listDeadLetter()` and export anything you need to keep: the older build does not read them, on either platform.

## Why This Changed

- **A promise could stay pending forever.** In `react-native-nitro-modules` 0.35.6 and 0.35.7, Nitro's Swift `Promise` had no lock, so a promise could settle before the generated bridge attached its listeners, and the JS promise never settled. The fix, [Nitro PR #1338](https://github.com/margelo/nitro/pull/1338), was first published in 0.35.8 on npm. Nitro's GitHub has no v0.35.8 release: the fix is listed in the [v0.35.9 release notes](https://github.com/margelo/nitro/releases/tag/v0.35.9), which compare v0.35.7 with v0.35.9, so 0.35.8 is the right floor. The library's own iOS change, which returns already-settled promises from its synchronous calls, stays and protects apps either way.
- **Failed items JS could not see.** A permanently failed item stayed in the queue store as a `FAILED` row that JS could not list, and on Android it counted toward `maxQueueSize`. In the dead-letter queue it can be listed, replayed or discarded, and it no longer counts toward the Android cap.
- **Duplicate connection events.** iOS emitted `CONNECTION_CHANGED` on every path update, including the first one and repeats of the same state.
- **False disconnects on Android.** Losing a secondary network, such as cellular alongside Wi-Fi or a VPN that does not apply to the app, reported `DISCONNECTED`. Following the default network also lets a VPN that was the default network hand over without a false disconnect.
- **Temporarily unmetered links.** On Android 11 and later, a link with `NET_CAPABILITY_TEMPORARILY_NOT_METERED` read as `METERED` with `isExpensive: true`.
