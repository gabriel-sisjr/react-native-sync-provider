# Migration Guide: v0.3.x to v0.4.0

> **Opt-in.** Nothing changes until you install a callback: with nothing installed, dispatch, retries, events and I/O behave as in v0.3.1. The only required change is at compile time, because `SyncErrorCode` gains two members. The rest of this guide is about adopting the new JS retry decider and dispatch interceptors. They run only while JS runs, and you install them first at startup.

## What Changed

- **Two error codes.** `SyncErrorCode` gains `RETRY_DECIDER_REJECTED` and `INTERCEPTOR_FAILED`, for 17 codes. An exhaustive `switch` with a `never` check stops compiling until it handles them. `SyncEventType` keeps its 16 events.
- **Retry decider.** [`setRetryDecider`](../api-reference/functions.md#setretrydecider) installs a JS function that the engine consults after an attempt fails with a retryable error and attempts are left. It answers `RETRY`, optionally with its own `delayMs`, `DROP` or `DEAD_LETTER`. [`clearRetryDecider`](../api-reference/functions.md#clearretrydecider) uninstalls it, and [`isRetryDeciderInstalled`](../api-reference/functions.md#isretrydeciderinstalled) reports the calling JS runtime's install. The `RetryPolicy` decides alone whenever the decider cannot answer, and wherever no JS runs.
- **Dispatch interceptors.** [`setHeaderResolver`](../api-reference/functions.md#setheaderresolver) supplies headers right before each request, [`setBeforeDispatch`](../api-reference/functions.md#setbeforedispatch) sees each request before it is sent and can `SKIP` it, and [`setAfterDispatch`](../api-reference/functions.md#setafterdispatch) observes each request that went out. Each one has a `clear…` function. A failing resolver or `beforeDispatch` fails closed: nothing is sent, and the item waits without spending an attempt.
- **`callbackTimeoutMs`.** A new `SyncOptions` field, default `3000` ms: how long the engine waits for an installed callback to answer.
- **Header layers.** With a resolver installed, headers merge as `defaultHeaders`, then the resolver's headers, then the item's own `headers`, a later layer winning. Names match case-insensitively.
- **One iOS detail.** Two header names that differ only by case inside one layer, such as `x-token` and `X-Token` in `defaultHeaders`, now resolve the same way on every run. Which one wins is still unspecified on both platforms, so do not send such pairs.
- **Persisted data.** No store schema changes. `callbackTimeoutMs` is persisted with the rest of the configuration, for cold starts.

## Migration Steps

### Step 1: Upgrade and Rebuild

1. Upgrade the package. The `react-native-nitro-modules` range is unchanged: 0.35.8 or later, and still below 0.36.
2. On iOS, run `cd ios && bundle exec pod install`, then rebuild. The pod ships new Swift sources.
3. On Android, rebuild. No new permission is needed.

### Step 2: Compile-Time Fixes

Add the two codes to any exhaustive `switch` that ends in a `never` check, and to any object typed `Record<SyncErrorCode, …>`:

```ts
import { SyncErrorCode } from '@gabriel-sisjr/react-native-sync-provider';

function describe(code: SyncErrorCode): string {
  switch (code) {
    case SyncErrorCode.NETWORK_ERROR:
      return 'No connection';
    // ...a case for each of the other 14 v0.3 codes
    case SyncErrorCode.RETRY_DECIDER_REJECTED:
      return 'Dropped or dead-lettered by the retry decider';
    case SyncErrorCode.INTERCEPTOR_FAILED:
      return 'Held back by a dispatch interceptor, tried again later';
    default: {
      const unreachable: never = code;
      return unreachable;
    }
  }
}
```

No call throws either code. The library reports them on events, and only once a callback is installed:

| Code                     | Reported on                                                                                                        | When                                                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RETRY_DECIDER_REJECTED` | `ITEM_FAILED`. After a `DEAD_LETTER`, also the dead letter's `lastErrorCode` and the `metadata.lastErrorCode` of `ITEM_DEAD_LETTERED` | The retry decider answered `DROP` or `DEAD_LETTER`                                                                                                      |
| `INTERCEPTOR_FAILED`     | `ITEM_RETRYING`, without a `statusCode`                                                                            | The header resolver or `beforeDispatch` failed or did not answer within `callbackTimeoutMs`, or `beforeDispatch` answered `SKIP`. Nothing was sent, and no attempt was spent |

If you mock the library in tests with an explicit factory, add the new functions your code calls.

### Step 3: Install Callbacks First at Startup

Skip this step if you adopt none of the new callbacks.

The first library call in a process starts the native engine, which can dispatch an item that is already due right away, and so can every `configureSync` call. An item that goes out before your `set…` call lands carries only the static headers and gets the `RetryPolicy`'s verdict. So make the `set…` calls the **first** library calls at startup: before `configureSync`, and before `<SyncProvider>` or any of the library's hooks mounts. `<SyncProvider>` configures from an effect that runs before your `App`'s own effects, so install at module scope of the entry file:

```js
// index.js
import { AppRegistry } from 'react-native';
import App from './src/App';
import { name as appName } from './app.json';
import { installSyncCallbacks } from './src/sync/installSyncCallbacks';

// Before anything else calls the library.
installSyncCallbacks().catch((e) => console.warn('Sync callbacks not installed', e));

AppRegistry.registerComponent(appName, () => App);
```

```ts
// src/sync/installSyncCallbacks.ts
import {
  setAfterDispatch,
  setBeforeDispatch,
  setHeaderResolver,
  setRetryDecider,
} from '@gabriel-sisjr/react-native-sync-provider';
import { decideRetry } from './decideRetry'; // Step 5
import { holdUploads, recordDispatch } from './dispatchHooks'; // Step 6
import { resolveHeaders } from './resolveHeaders'; // Step 4

export function installSyncCallbacks(): Promise<void[]> {
  // Start every call before awaiting any of them.
  return Promise.all([
    setHeaderResolver(resolveHeaders),
    setBeforeDispatch(holdUploads),
    setAfterDispatch(recordDispatch),
    setRetryDecider(decideRetry),
  ]);
}
```

Install only the callbacks you need. Then configure as you do today, through `configureSync` or `<SyncProvider options>`.

- **Installing first keeps the window short; it does not close it.** Calls started back to back all reach native in one turn of JS, but an item due at that moment can still go out with the static headers alone.
- **Install unconditionally.** A repeated `set…` replaces the callback the same JS runtime installed. `clear…` and `isRetryDeciderInstalled()` see only the calling runtime's installs, and a fresh runtime starts with none, so do not guard the install with `isRetryDeciderInstalled()`.
- **After a JS reload,** the old runtime's callbacks never answer again, but its installs stay in place until the new JS makes its first library call. On iOS they fail at once, without calling JS, and on Android each consult first waits `callbackTimeoutMs`. Either way, the decider's items get the policy's verdict, the resolver's and `beforeDispatch`'s items are deferred, and an `afterDispatch` call is only logged. See [Reloads and Teardown](../guides/dispatch-interceptors.md#reloads-and-teardown).
- **Pass arrow functions or bound methods.** The library calls your function without a `this`, so a method that reads `this`, passed as `setHeaderResolver(auth.getHeaders)`, fails on every call, and every item is deferred. Write `setHeaderResolver(() => auth.getHeaders())`.
- **Never await `flush()` inside a callback.** On Android it stalls the cycle until `callbackTimeoutMs`, and then the fallback or the deferral applies. On iOS it returns the last result at once.
- **Keep secrets out of error messages.** Native logs up to 256 characters of a callback's `Error` message, as private data on iOS and to logcat on Android. A thrown value that is not an `Error` is described by its type only.

### Step 4: Move Token Refresh to a Header Resolver (Optional)

In v0.3, a token reached the requests only through `defaultHeaders`, so the app pushed it with `configureSync` at every change, and a request could go out with a token that had expired since the last push. A header resolver supplies it right before each request, retries included.

#### Before

```ts
// At launch, and again after every token refresh.
await configureSync({
  ...SYNC_OPTIONS, // your existing options
  defaultHeaders: { Authorization: `Bearer ${token}` },
});
```

#### After

Keep that `configureSync` call: the `defaultHeaders` it stores are what a process with no JS sends. Add the resolver for the requests sent while JS runs:

```ts
// src/sync/resolveHeaders.ts
import type { HeaderResolver } from '@gabriel-sisjr/react-native-sync-provider';
import { getValidAccessToken } from '../auth'; // your app: the token, refreshed when it expires

let refreshing: Promise<string> | null = null;

// Overlapping calls share one refresh: Android resolves up to batchSize items at once.
function accessToken(): Promise<string> {
  if (!refreshing) {
    refreshing = getValidAccessToken().finally(() => {
      refreshing = null;
    });
  }
  return refreshing;
}

// When the refresh fails, the throw defers the item: nothing is sent.
export const resolveHeaders: HeaderResolver = async () => ({
  Authorization: `Bearer ${await accessToken()}`,
});
```

Where no JS runs, as in a cold background worker or a BGTask launch, no resolver is installed, and only the stored `defaultHeaders` go out:

| Setup                                           | While JS runs                                            | With no JS: a cold worker or a BGTask launch                        |
| ----------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------- |
| The resolver, and the token in `defaultHeaders` | The resolver's `Authorization` wins over the stored one  | The stored token goes out. A 401 or 403 holds the item, as in v0.3 |
| The resolver only                               | The resolver's token goes out                            | No token goes out. A 401 is terminal and dead-letters the item      |

Keep the token in `defaultHeaders`, and keep calling `configureSync` when it changes, unless the requests sent without JS need no credential. See [When a Stored Token Expires](../guides/background-sync.md#when-a-stored-token-expires). Before you rely on the resolver:

- **The credential rules are unchanged.** A 401 or 403 is handled as in v0.3, whoever supplied the header. In a process that has called `configureSync`, it is terminal: the item is dead-lettered with `UNAUTHORIZED`, and the retry decider is not consulted. A request sent on `defaultHeaders` restored from storage, in a process that has not called it, is held instead. So refresh the token before it expires, and after a forced sign-in, replay the `UNAUTHORIZED` dead letters, as in [Dead-Letter Flows](../guides/error-handling.md#dead-letter-flows).
- **Throw when there is no token.** A throw, a rejection, an invalid result or no answer within `callbackTimeoutMs` defers the item: nothing is sent, no attempt is spent, and the item is due again after the policy's delay for its next attempt, and no sooner than 60 s, with `ITEM_RETRYING` and `INTERCEPTOR_FAILED`. Returning `{}` is a valid answer: the request then goes out with the static headers alone.
- **Return a plain object of strings.** Each name must be non-empty and use only the characters from `!` to `~`, and each value only tab and the characters from space to `~`. Anything else is an invalid result. Names match the other layers case-insensitively, and the winning layer's spelling is kept.
- **Leave credentials out of item `headers`.** An item's own headers win over the resolver's, so an `Authorization` set at enqueue time overrides the fresh token. Item headers are also stored in plain text.
- **Logout is unchanged.** Call `configureSync` without `defaultHeaders`, then `clearQueue()`. A resolver that throws while no one is signed in keeps anything enqueued later from going out without a session.
- **Background uploads on iOS** carry the headers resolved when their task was created.
- **The probes are untouched.** The health-check and network-quality probes never call a callback, so they carry no resolver headers.

For a version that refreshes only near expiry, see [Token Refresh](../guides/dispatch-interceptors.md#token-refresh).

### Step 5: Adopt the Retry Decider (Optional)

```ts
// src/sync/decideRetry.ts
import {
  RetryAction,
  type RetryDecider,
} from '@gabriel-sisjr/react-native-sync-provider';

export const decideRetry: RetryDecider = ({ attempt, statusCode, metadata }) => {
  if (metadata?.kind === 'analytics' && attempt >= 2) {
    return { action: RetryAction.DROP }; // deleted, with no dead letter
  }
  if (statusCode === 503) {
    return { action: RetryAction.RETRY, delayMs: 5 * 60_000 }; // used as given
  }
  return { action: RetryAction.RETRY }; // the policy's delay
};
```

- **When it is consulted.** Only after an attempt fails with a retryable error and attempts are left. Never for a success, a non-retryable failure such as a 404, a spent budget, a credential hold or an item that was never sent. It can veto a retry or change its delay, but it cannot retry what the `RetryPolicy` would not, nor add attempts. Its context carries the 1-based `attempt` that just failed, that attempt's `errorCode`, the `statusCode` when an HTTP answer came back, and the item's `itemId`, `url`, `method` and `metadata`.
- **`RETRY`.** `ITEM_RETRYING` keeps the attempt's real code. A `delayMs` that is finite and at least `0` replaces the policy's delay: it is truncated and used as given, with no jitter and no `maxDelayMs` cap. A missing `delayMs` means the policy's delay, and so does an invalid one, which is logged as a warning. Once a decider is consulted, the delay counts from the decision, not from the end of the attempt.
- **`DEAD_LETTER`.** The item moves to the dead-letter queue with `lastErrorCode: RETRY_DECIDER_REJECTED`, and `lastErrorMessage` keeps the real failure. `ITEM_FAILED` reports `RETRY_DECIDER_REJECTED` with the attempt's `statusCode`, then `ITEM_DEAD_LETTERED` follows.
- **`DROP`.** The item is deleted, with `ITEM_FAILED` and no dead letter. It is the one exception to "an item that fails permanently is not dropped". On Android it also appears in `failedIds` and `errors`. Both `DROP` and `DEAD_LETTER` count in `failureCount`.
- **The policy still decides alone** when no decider is installed; when it throws, rejects, returns an invalid decision or does not answer within `callbackTimeoutMs`; when the JS runtime that installed it was torn down or replaced; and when a BGTask expires or the cycle is cancelled during the wait. Keep the `RetryPolicy` tuned: it is the only rule where no JS runs.

See the [Retry Policy guide](../guides/retry-policy.md) for how the two work together.

### Step 6: Hold or Observe Requests (Optional)

```ts
// src/sync/dispatchHooks.ts
import {
  BeforeDispatchAction,
  type AfterDispatchHook,
  type BeforeDispatchHook,
} from '@gabriel-sisjr/react-native-sync-provider';
import { metrics, uploadSettings } from '../app'; // your app

// Hold uploads while the user has paused them.
export const holdUploads: BeforeDispatchHook = ({ metadata }) =>
  metadata?.kind === 'upload' && uploadSettings.paused
    ? { action: BeforeDispatchAction.SKIP }
    : undefined; // no action key: proceed

// Trace each request that went out. Dispatch does not wait for it.
export const recordDispatch: AfterDispatchHook = ({ url, outcome, durationMs }) => {
  metrics.record(url, outcome, durationMs);
};
```

- **`SKIP` defers the item** the way a failing resolver does: nothing is sent, no attempt is spent, and `ITEM_RETRYING` reports `INTERCEPTOR_FAILED`. Return the object `{ action: BeforeDispatchAction.SKIP }`: a result without an `action` key proceeds, a bare `'SKIP'` string included, and an `action` other than `PROCEED` or `SKIP` is a failure.
- **What `beforeDispatch` sees.** The merged headers, without the implicit `Content-Type` fallback, the stored `contentType` and the item's `metadata`, never the body. On Android, the body's media type replaces a header layer's `Content-Type` on the wire.
- **`afterDispatch` is never awaited.** It is called once for each request that went out, after the outcome is stored and the item's event is emitted. `flush()` may resolve before it runs, and its order after the item's event is best effort. `durationMs` covers the request alone, without any callback wait. It never receives headers or a body, and its errors and timeouts are only logged. On iOS, an upload that completes after a relaunch gets no `afterDispatch`.

See the [Dispatch Interceptors guide](../guides/dispatch-interceptors.md) for the order of the steps around each request.

### Step 7: Tune `callbackTimeoutMs` (Optional)

```ts
await configureSync({
  ...SYNC_OPTIONS, // your existing options
  defaultHeaders: session.headers, // keep them on every call
  callbackTimeoutMs: 5000, // the default is 3000
});
```

- **One bound for all four callbacks.** It holds even when a callback's promise never settles. When it runs out, the decider's item gets the policy's verdict, the resolver's or `beforeDispatch`'s item is deferred, and an `afterDispatch` call is only logged.
- **Validation.** `configureSync` rejects a value that is not a finite number of at least `1` with `INVALID_PAYLOAD` and `validationErrors`, before anything is applied or stored. Fractions truncate, and a value above 2147483647 ms is capped there when used. It is persisted for cold starts, `getSyncConfig()` returns it only when it was set, as given, and a stored value that cannot be used loads as unset.
- **Pick it from your slowest refresh.** Too low, and a slow token refresh defers every item waiting on it. Too high, and a hung JS thread costs that much for each awaited callback. iOS sends one item at a time, so the cost adds up item by item. On Android, a batch's callbacks wait at the same time.

### Step 8: Review Behavior Your Code May Rely On

Nothing below applies until a callback is installed.

| Area | What changes once a callback is installed | What to do |
| --- | --- | --- |
| `ITEM_RETRYING` | Can report `INTERCEPTOR_FAILED`, with no `statusCode` and the `attempt` the item would have been. Nothing was sent. | Do not count it as a failed request. |
| `ITEM_FAILED` | Can report `RETRY_DECIDER_REJECTED`, with the attempt's `statusCode`. | After a `DEAD_LETTER`, read the real failure from the dead letter's `lastErrorMessage`. |
| Dropped items | A decider's `DROP` deletes the item: no dead letter and no `ITEM_DEAD_LETTERED`. | Count drops on `ITEM_FAILED` if you need them. |
| `failureCount` | Counts a decider's `DROP` and `DEAD_LETTER`. A deferral counts in neither total. | Nothing. |
| Retry timing | Once a decider is consulted, the delay counts from the decision. A valid `delayMs` is used as given, with no jitter and no `maxDelayMs` cap. | Spread your own delays if many items fail together. |
| Deferred items | A failing resolver or `beforeDispatch` holds its items, at least 60 s apart, without spending attempts, and never dead-letters them. Cycles still end with `SYNC_SUCCEEDED`. | Watch `ITEM_RETRYING` for `INTERCEPTOR_FAILED`. See [When an Interceptor Fails](../guides/dispatch-interceptors.md#when-an-interceptor-fails). |
| Cycle duration | Each awaited callback can take up to `callbackTimeoutMs`. iOS sends one item at a time, and Android runs a batch's callbacks at once. | Keep callbacks fast. |
| `getPendingItems()` | During an interceptor wait, the item is included on iOS and left out on Android. | Do not rely on either. |
| `configureSync` during a wait | Applies from the next item on iOS and from the next cycle on Android. | Nothing. |
| `Content-Type` | On Android, the body's media type replaces a header layer's `Content-Type` on the wire, so `beforeDispatch` can see one that the request will not carry. | Set `contentType` on the item, and leave `Content-Type` out of every header layer, the resolver's included. |
| Logs | Up to 256 characters of a callback's error message reach the native log: as private data on iOS, and to logcat on Android. | Keep secrets out of the errors your callbacks throw. |

See [Platform Differences](../guides/dispatch-interceptors.md#platform-differences) for the full list.

### Rolling Back {#rolling-back-from-v04}

v0.4 changes no store schema, so a rollback to v0.3 needs no data step. First remove the calls to the new functions and the two new `case`s: v0.3 has neither.

A v0.3 build ignores a persisted `callbackTimeoutMs`. A dead letter that v0.4 wrote with `RETRY_DECIDER_REJECTED` reads back in v0.3 as `MAX_ATTEMPTS_EXCEEDED`, the code v0.3 reports for any stored code it does not know, and its `lastErrorMessage` still names the real failure. Both outcomes follow from the code and have not been exercised in a test.

## Checklist

- [ ] `RETRY_DECIDER_REJECTED` and `INTERCEPTOR_FAILED` are handled in every exhaustive `switch` over `SyncErrorCode` and every `Record<SyncErrorCode, …>`.
- [ ] Test mocks built with an explicit factory include the new functions your code calls.
- [ ] The `set…` calls are the first library calls at startup, before `configureSync`, `<SyncProvider>` and every hook, and they run unconditionally.
- [ ] Every callback is an arrow function or a bound method, and none awaits `flush()`.
- [ ] The header resolver shares one token refresh between overlapping calls, and throws when it has no token.
- [ ] A credential that requests need without JS is still in `defaultHeaders`, and `configureSync` still runs when it changes.
- [ ] No credential sits in an item's own `headers`.
- [ ] `callbackTimeoutMs` is above your slowest token refresh.
- [ ] Event handlers treat `ITEM_RETRYING` with `INTERCEPTOR_FAILED` as a deferral, and `ITEM_FAILED` with `RETRY_DECIDER_REJECTED` as the decider's verdict.
- [ ] The errors your callbacks throw carry no secrets in their messages.

## Why This Changed

- **Retry rules that depend on the app.** The declarative `RetryPolicy` applies one rule to every item: a status-code allowlist and a backoff. It cannot give up early on a low-value request, or wait longer for one endpoint. The decider adds that while JS runs, and the policy keeps deciding where no JS runs.
- **Tokens that expire in the queue.** Headers were static: the stored `defaultHeaders` and the item's own. A token had to be pushed with `configureSync` at every change, and a request could go out with one that had expired since. A header resolver supplies the token right before each request.
- **Holding and tracing requests.** `beforeDispatch` lets the app hold a request it should not send yet, and `afterDispatch` lets it trace each request that went out.
- **Failing closed.** A failing resolver or `beforeDispatch` defers the item instead of sending it without the headers it needs, and the attempt is not spent, so a broken token source does not burn through the retry budget.
