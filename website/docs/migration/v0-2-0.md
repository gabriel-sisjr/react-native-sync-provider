# Migration Guide: v0.1.x to v0.2.0

> **Native changes on iOS.** No function, hook or error code was removed. The upgrade does need native changes on iOS, and several behaviors changed, so read the whole list before you ship it. Most entries are observable behavior changes rather than renamed APIs. Start with the first one: it is the only one that can stop an app from launching.

## What Changed

- **No app-side `BGTaskScheduler` registration.** The library registers its BGTask handlers at process start, through `+load`, before `application(_:didFinishLaunchingWithOptions:)` runs. iOS traps on a second `register` for the same identifier, so an app that still registers a library identifier is expected to crash at launch. A missing identifier no longer crashes: its handler is skipped, and `enableBackgroundSync` rejects when `.background` is the one missing.
- **iOS 15.0 minimum.** The deployment target declared in `SyncProvider.podspec` moves from `13.0` to `15.0`. React Native 0.85 raises the built pod to `15.1`.
- **Required fields.** `SyncItem.attempts`, `SyncItem.nextRetryAt` and `SyncProviderContextValue.hasProvider` are required.
- **Queue reads cover `PENDING` items only.** `getQueueSize()` and `getPendingItems()` report items waiting to be dispatched, on both platforms, cooling items included. `getPendingItems()` returns dispatch order on both.
- **Real error codes on iOS.** A non-retryable failure on an item's last attempt keeps its real code, so a 401 stays `UNAUTHORIZED`. Android already behaved this way.
- **`MANUAL` and pauses.** `strategy: MANUAL` suppresses the in-process retry timer and the Android retry kick, not workers or BGTasks. `pauseSync()` is persisted.
- **Persisted configuration.** `configureSync` persists its options, so a worker or BGTask in a fresh process honors them. `defaultHeaders` are encrypted at rest, and a call without them deletes the stored copy.
- **Persisted retry cooldowns.** Both platforms persist the cooldown as `SyncItem.nextRetryAt` and skip an item until it passes. Each cycle makes at most one attempt per item.
- **`enqueueBatch` validation.** An invalid batch throws one `INVALID_PAYLOAD` whose new `validationErrors` field lists every issue of every item. The new `ValidationIssue` type describes each one.
- **Schema migrations.** Room v1→v2 on Android and Core Data model v2 on iOS persist `nextRetryAt`. They migrate forward automatically and have no supported downgrade.
- **Privacy Manifest.** The library's manifest adds `NSPrivacyAccessedAPICategoryUserDefaults` with reason `CA92.1`.

## Migration Steps

> **Important — Do this first on iOS:** If your `AppDelegate` calls `BGTaskScheduler.shared.register` for a library identifier, delete that call. The library now registers its handlers at process start, and iOS traps on a second registration, so the app is expected to crash at launch. This is expected rather than reproduced on a device.

### Step 1: iOS Native Changes

1. Delete any `BGTaskScheduler.shared.register` call for `com.gabriel-sisjr.syncprovider.background` or `com.gabriel-sisjr.syncprovider.processing`. No `AppDelegate` code is needed for registration.
2. Declare both identifiers under `BGTaskSchedulerPermittedIdentifiers`. Older instructions listed only the first one. Without `.processing`, the longer task never runs.
3. Check that `UIBackgroundModes` has `fetch` and `processing`.
4. Forward background `URLSession` events from your `AppDelegate`:

```swift
import SyncProvider

func application(
  _ application: UIApplication,
  handleEventsForBackgroundURLSession identifier: String,
  completionHandler: @escaping () -> Void
) {
  HybridSyncProvider.handleBackgroundURLSessionEvents(
    identifier: identifier,
    completionHandler: completionHandler
  )
}
```

5. Raise the deployment target to at least `15.0`, in `ios/Podfile` and anywhere you set `IPHONEOS_DEPLOYMENT_TARGET`.
6. Run `cd ios && bundle exec pod install`.

The Privacy Manifest now declares `NSPrivacyAccessedAPICategoryUserDefaults` / `CA92.1`. It is merged for you.

### Step 2: Compile-Time Fixes

`SyncItem.attempts`, `SyncItem.nextRetryAt` and `SyncProviderContextValue.hasProvider` are required. Code that only reads these types compiles as before. Hand-built values, usually test fixtures, need the new fields:

```ts
const item: SyncItem = {
  id,
  method: 'POST',
  url,
  createdAt: 0,
  attempts: 0,
  nextRetryAt: 0,
};
const value: SyncProviderContextValue = { config, hasProvider: true };
```

`attempts: 0` means no attempt has been recorded, and `nextRetryAt: 0` means the item is eligible now. Neither one means the item was never tried.

### Step 3: Configuration and Credentials

`configureSync` now persists its options, so a worker or BGTask with no JS honors them. `defaultHeaders` are encrypted at rest.

- Call `configureSync` at launch and whenever the token changes. The library does not refresh tokens.
- Pass `defaultHeaders` on every call that should keep them, including through `<SyncProvider options>`. Each call replaces the whole configuration, and omitting them deletes the stored copy.
- Call `configureSync` without `defaultHeaders` on logout.
- Move credentials out of per-item `headers`, which are stored in plain text.

In a process that has not called `configureSync`, a 401 or 403 now holds the item instead of failing it. See [When a stored token expires](../guides/background-sync.md#when-a-stored-token-expires).

### Step 4: Review Behavior Your Code May Rely On

| Area | What changed | What to do |
| --- | --- | --- |
| New items | Earlier docs said `AUTOMATIC` flushes on enqueue and on reconnect. It never did. | Mount [`useAutoSync`](../api-reference/hooks/useAutoSync.md) or call `flush()`. |
| Retries | Failed items wait out a persisted `nextRetryAt`, on both platforms, and a timer brings them back while the app runs. | Do not expect the next `flush()` to re-send a failed item. Use `drainUntilEmpty()`, which sleeps through cooldowns. See [Retry cooldown](../guides/retry-policy.md#retry-cooldown-across-restarts). |
| Cycles | A cycle where every item is cooling is `SYNC_SUCCEEDED` with 0/0. An empty cycle is too, now also on Android. | Check `successCount` rather than treating `SYNC_SUCCEEDED` as delivery. |
| `getQueueSize()`, `getPendingItems()` | `PENDING` items only, on both platforms. Cooling items are included. Android stopped counting `FAILED` and in-flight rows, and iOS stopped returning them. | Listen to `ITEM_FAILED` for permanent failures, and check `isSyncing()` as well as the size. |
| `MANUAL` | It stops the retry timer and the Android kick. It does not stop workers or BGTasks. | Use `foregroundOnly: true` to stop background work. |
| `pauseSync()` | Persisted. Workers stay inert while the app is dead. Lasts until `resumeSync()` or the next launch. | Call `pauseSync()` at startup to keep a pause across launches. |
| Error codes on iOS | A non-retryable failure keeps its real code on the last attempt, so a 401 stays `UNAUTHORIZED`. `MAX_ATTEMPTS_EXCEEDED` is only for a retriable failure with no attempts left. | Handle `UNAUTHORIZED` and `SERVER_ERROR` on `ITEM_FAILED`. |
| `enqueueBatch` | Throws one `INVALID_PAYLOAD` with `validationErrors`, instead of the first item's code. Array holes are rejected. | Branch on `INVALID_PAYLOAD`, and read `err.validationErrors`. See [Errors](../api-reference/errors.md#batch-validation-aggregates-all-issues). |
| `ValidationIssue.value` | Set only for `method`, `priority` and `contentType`. | Do not expect it for `url`, `body`, `headers` or `metadata`. |

### Step 5: Remove Options That Do Nothing

These were always accepted and never applied. They still compile, but the docs no longer present them as working:

- `SyncOptions.persistQueue`: the queue is always persisted.
- `BackgroundSyncOptions.taskIdentifier`: both platforms use fixed identifiers. Remove any custom identifier from `Info.plist`.
- `useAutoSync({ backgroundSync })` and `useAutoSync({ flushOnForeground })`: use `enableBackgroundSync` and `flushOnAppForeground`.

`useAutoSync({ intervalMs: 0 })` does not turn the interval off: it falls back to 60 seconds.

### Queue Data

Room v1→v2 on Android and Core Data model v2 on iOS migrate forward automatically on first launch and preserve queued items. There is nothing to do.

### Rolling Back

> **Important — Android downgrade wipes the queue:** Downgrading an Android install past v0.2 triggers `fallbackToDestructiveMigrationOnDowngrade()` and wipes the persisted queue. There is no supported downgrade.

If you must roll back, drain the queue first with `drainUntilEmpty()` and confirm `stoppedReason === 'EMPTY'`: any other reason means items remain. Otherwise, accept that the older build recreates the Android queue from scratch. Recovery from a regression is a new forward migration, never a revert, so pin or roll forward rather than ship a downgrade across the v0.2 schema boundary with a queue you need to keep.

## Why This Changed

- **Registration in the app could crash it.** Earlier versions of the iOS setup page showed an optional block that registered `com.gabriel-sisjr.syncprovider.background` in `didFinishLaunchingWithOptions`. That block also called `SyncProviderBackgroundTaskRunner`, a class the library never shipped. Registering at process start needs no `AppDelegate` code.
- **The `13.0` floor was latent.** The dispatcher uses the async `URLSession.data(for:)` API, which requires iOS 15. The build only passed because the example app overrode `IPHONEOS_DEPLOYMENT_TARGET`, and any consumer honoring the declared `13.0` floor would have hit an availability compile error.
- **Hot retry loops.** On iOS, failed-retriable items returned to `PENDING` with no cooldown, so they were re-dispatched on the next cycle: a hot retry loop against a degraded server. On Android, backoff lived inside a single cycle and was lost on a restart.
- **Cold workers had no configuration.** A worker or BGTask in a fresh process ran on the defaults and with no default headers.
- **Errors end up in logs.** `ValidationIssue.value` is never set for `url`, `body`, `headers` or `metadata`, because those fields can hold credentials and personal data. `reason` does not contain the URL.
