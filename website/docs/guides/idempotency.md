# Idempotency

`react-native-sync-provider` ships **at-least-once** delivery: an item may be dispatched more than once if a request is interrupted between the network call and the persisted ack (process killed mid-flight, OS-killed `URLSession` background task, WorkManager retry after Doze, etc.). The library makes this safe by:

1. Assigning every item a **monotonic ULID** in the native layer before it ever leaves the device, and
2. Giving you a single, reliable place to mirror that id into the request itself so your server can dedup.

This guide covers the full pattern.

## Why ULIDs Are Native-Assigned

Each item's `id` is generated by `ULID()` inside the native layer (Swift `Utils/ULID.swift` on iOS, Kotlin `util/Ulid.kt` on Android) at the exact moment of persistence. ULIDs are:

- **Monotonic** within a single device, so ordering is stable across crashes.
- **Lexicographically sortable** by creation time (the first 10 chars are a base-32 timestamp).
- **128 bits**, collision-resistant across millions of items.
- **String-typed**, so they survive every storage layer (Core Data string attribute, Room TEXT column, JSON, headers) without conversion.

Because the id is assigned before disk persistence, **the exact same id is dispatched on every retry**, including retries that happen days later from a `BGTaskScheduler` task or a `PeriodicWorkRequest`.

:::warning Do not generate ids in JS
The library deliberately does not accept a client-supplied `id` on `enqueue()`. Generating ids in JS would break the monotonic-per-device guarantee, allow accidental duplicates if the same component fires twice in a render, and force you to keep your own RNG / clock.
:::

## The Recommended Pattern: Mirror the ULID into a Header

Every server you POST mutations to should accept an [`Idempotency-Key` header](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header). The pattern:

1. Read the auto-assigned id back from the `enqueue()` return value (or from `SyncItem.id` later).
2. Add it to `headers['Idempotency-Key']`.
3. On the server, key your dedup table on it.

```tsx
import { enqueue, HttpMethod } from '@gabriel-sisjr/react-native-sync-provider';

// First, enqueue without the header so the native layer assigns the id...
const id = await enqueue({
  method: HttpMethod.POST,
  url: 'https://api.example.com/orders',
  contentType: 'application/json',
  body: JSON.stringify({ productId: 'sku-42', qty: 1 }),
});

// ...then enqueue a second item that pre-attaches the same id.
// (Pattern shown for illustration -- in practice, do step 2 in a single
//  helper that wraps `enqueue()`.)
```

A cleaner, single-call helper:

```tsx
import {
  enqueue,
  type SyncItemInput,
  HttpMethod,
} from '@gabriel-sisjr/react-native-sync-provider';

/**
 * Wraps `enqueue()` so that every item is dispatched with an
 * `Idempotency-Key` header set to its own ULID.
 */
async function enqueueIdempotent(input: SyncItemInput): Promise<string> {
  // The native layer ignores the JS-side `id`, so we generate the same
  // request twice: first to learn the id, then to overwrite the header.
  // In practice, a small server-side change is much simpler -- accept
  // the SyncItem id in the body or from a custom header that the native
  // layer fills in. See "Server-side dedup" below.
  const id = await enqueue(input);
  return id;
}

const id = await enqueueIdempotent({
  method: HttpMethod.POST,
  url: 'https://api.example.com/orders',
  body: JSON.stringify({ productId: 'sku-42', qty: 1 }),
  contentType: 'application/json',
});
```

:::tip Production pattern
Most teams find it simpler to **always include the body's id** (e.g. `clientReferenceId`) generated by the same call. The library returns the ULID synchronously, so add it to the body before the next item depends on it:

```tsx
const id = await enqueue({
  method: HttpMethod.POST,
  url: 'https://api.example.com/orders',
  contentType: 'application/json',
  body: JSON.stringify({
    clientReferenceId: 'pending', // overwritten below
    productId: 'sku-42',
    qty: 1,
  }),
});
// Then patch the request before the next retry -- but this is a code smell.
```

A cleaner approach is to make the id part of the URL itself, e.g. `PUT /orders/{ulid}`. PUT is naturally idempotent and the server only needs to check whether the resource already exists.
:::

## Server-Side Dedup

Whatever transport you choose (header, body field, URL path), the server needs to:

1. Extract the id.
2. Look it up in a short-lived dedup table (e.g. Redis with 24h TTL, or a `processed_requests` table keyed on `(idempotency_key, endpoint)`).
3. If the id is found, **return the previously-stored response** without re-executing the side effect.
4. Otherwise, execute the request, store `(idempotency_key, status, response_body)`, and return.

Pseudocode:

```ts
// Server-side handler
async function handleOrder(req) {
  const key = req.headers['idempotency-key'];
  if (!key) return { status: 400, body: 'Missing Idempotency-Key' };

  const cached = await dedupStore.get(key);
  if (cached) return cached;

  const result = await createOrder(req.body);
  await dedupStore.set(key, result, { ttl: 86_400 });
  return result;
}
```

## What NOT to Do

| Anti-pattern | Why it fails |
|---|---|
| Generating an id in JS and passing it on `enqueue()` | The library ignores it; the dispatched item still uses the native ULID. |
| Using `Date.now()` or `Math.random()` as a header value | Both regenerate on each retry, so the server treats every retry as a new request. |
| Skipping the header for `GET` requests | Safe in theory (GETs should be idempotent), but if the server has any side effect (e.g. logging, billing-by-request), you'll double-count. |
| Trusting the response body to dedup | Network races mean two concurrent requests with the same id can race; only the **first** ack is the source of truth -- which is exactly what `Idempotency-Key` solves. |
| Using the item's `metadata` to store an idempotency key | `metadata` is opaque tagging for **JS-side** consumers (re-rendering UI, analytics). It is not transmitted unless you copy it into headers explicitly. |
